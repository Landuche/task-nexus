# Theoretical questions

## 1. Rendering strategies in React and Next.js

### a) CSR, SSR and SSG

**Client-Side Rendering (CSR).** The server sends a nearly empty HTML shell and a JavaScript bundle. The browser runs the JavaScript, fetches data, and builds the UI. Once loaded, navigation is fast because only data moves over the network.

**Server-Side Rendering (SSR).** The server runs React for each request and sends fully rendered HTML with the current data. The browser then "hydrates" that HTML, attaching event handlers to it so it becomes interactive.

**Static Site Generation (SSG).** The HTML is rendered once, at build time, and served as static files, usually from a CDN. No server code runs per request. Data is only as fresh as the last build (Next.js also offers incremental static regeneration to refresh pages in the background).

### b) When each approach fits

- **CSR** works well for authenticated, highly interactive apps where SEO does not matter: internal dashboards, design tools, admin panels. The downside is a blank or skeleton first paint and weaker results for crawlers that do not run JavaScript.
- **SSR** fits pages whose content is personalized or changes often and must be indexed: product pages with live price and stock, news feeds, account pages. The cost is a server render on every request, and the time to first byte depends on how fast the data loads.
- **SSG** fits content that changes rarely and must be very fast and cheap to serve: documentation, marketing pages, blog posts. It becomes a problem when the content is per-user or changes every few minutes, because either the data is stale or you rebuild too often.

In this project, the task list uses SSR (`dynamic = "force-dynamic"`) because the data is changed by the user at any time. The server returns the first page already rendered, and the client takes over for filtering, pagination and mutations.

## 2. Backend approaches

### a) Common ways to implement a backend

- **Server-rendered monolith** (Rails, Django, Laravel): HTML is generated by the server and forms are posted back. Simple and productive, with less client-side complexity.
- **REST API + separate SPA** (Express, Fastify, NestJS): resources are exposed over HTTP. REST is widely understood, cacheable and works with any client, which makes it the usual choice for public APIs.
- **GraphQL** (Apollo, Yoga): the client describes the shape of the response it needs. Useful with many clients and varied data needs, but it adds complexity in caching, authorization per field and query cost control.
- **RPC-style APIs** (tRPC, gRPC, JSON-RPC): the client calls named procedures. Very direct to write and, with tRPC, fully typed across the wire.
- **Backend as a service** (Firebase, Supabase): the backend is managed. Fastest to start, with less control over data rules and vendor lock-in.
- **Framework-integrated server functions** (Next.js Server Actions, Remix actions): mutations live next to the UI code, with no separate API layer.

The main trade-offs are control versus speed of delivery, how many clients consume the API, the team's language choices, and how the system needs to scale.

### b) tRPC

tRPC lets the frontend call backend procedures with full TypeScript inference, without code generation. Input and output types flow from the router to the client automatically, and Zod schemas validate inputs at runtime.

**Advantages**

- **Typing:** renaming a field on the server breaks the client at compile time.
- **Developer experience:** a thin layer over HTTP with a small API surface and direct integration with React Query.
- **Security, when used well:** a single validation boundary per procedure (Zod). Schemas that reject unknown keys prevent mass assignment.
- **Scalability:** it is plain HTTP, so it scales like any stateless API. Batching reduces the number of requests.

**Disadvantages and risks**

- **TypeScript on both sides.** Teams that use other languages, or that need a public API, lose the main benefit. Tools such as OpenAPI and client SDKs in other languages are not provided out of the box.
- **Coupling.** Frontend and backend types evolve together, which suits a monorepo well but makes independent deployments and versioning harder.
- **Types are not validation.** TypeScript types disappear at runtime. Every input still needs a runtime schema, or the type system gives false confidence.
- **Authorization is not automatic.** Procedures are public unless a middleware says otherwise, so access control has to be designed explicitly.
- **HTTP semantics.** Queries are sent as GET and mutations as POST. Good caching and CSRF protection depend on configuration and on keeping mutations off GET, which tRPC enforces by default.
